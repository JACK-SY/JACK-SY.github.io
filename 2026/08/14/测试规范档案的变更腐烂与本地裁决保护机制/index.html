测试规范档案的变更腐烂与本地裁决保护机制

JACK-YANG
测试管理 测试管理

发布于：2026年8月14日

面向团队全体成员 | 2026-08-14 | 测试工程师 + Claude

一句话概括

本文解决两个在 AI 协作测试管理中反复出现的痛点：规范导航表随文件增删逐渐失效和本地PRD有用户确认但知识库还没同步时被覆盖。对应的两个机制是：变更协议 + 自检脚本和本地裁决标注 + 同步检查矩阵。

问题一：静态导航表的变更腐烂

痛点

项目有 12 份测试规范文档，AGENTS.md 作为 Agent 的唯一入口，用静态表格登记了每份文件的路径、用途、读取时机。问题出在：

  • 有人新增了一份规范文件，忘了在 AGENTS.md 的文件清单表和读取机制表里登记 → Agent 读取时不知道这份文件存在 → 新规范写了等于没写
  • 有人删除了一份规范文件，忘了在 AGENTS.md 里移除路径 → Agent 照着失效路径去找 → 找不到 → 出错或忽略
  • 有人改了章节号（如 §8.7 改为 §8.8），其它文件里交叉引用还写着 §8.7 → 引用断链 → Agent 读到错误的章节

这三类问题在文档项目里几乎是必然发生的——文件增删改是常态，但全靠人工记得同步登记表，迟早遗漏。这叫变更腐烂：每次变更漏一点，积累下来导航表和实际文件就脱节了。

解决方法

两层防线：

第一层：变更协议（AGENTS.md §规范文件变更协议）

在 AGENTS.md 中显式定义文件增删改时必须同步的操作清单：

操作 必须同步更新 操作后执行
新增文件 ① AGENTS.md 文件清单表登记路径 ② AGENTS.md 读取机制表添加对应行 ③ 总纲 §2 关联规范速查表 运行自检脚本
删除文件 ① AGENTS.md 文件清单表移除 ② AGENTS.md 读取机制表移除 ③ 所有引用改为替代或删除 运行自检脚本
改章节号 所有引用该章节号的文件 运行自检脚本
改内容不改章节号 无 无需操作

第二层：自检脚本（测试规范档案/_spec_health_check.py）

人记不住的，脚本来兜底。3 秒内检测 3 类问题：

检测项 检测方式 发现问题时
文件清单一致性 对比实际文件 vs AGENTS.md 登记的路径 报 ERROR：文件存在未登记 / 已登记但文件不存在
交叉引用有效性 正则提取所有 《文件名》§章节号 引用，校验目标文件和章节是否存在 报 ERROR：目标文件不存在 / 章节号断链
文件计数 对比 AGENTS.md 声明的文件数 vs 实际文件数 报 WARNING：数量不一致

效果

  • 新增文件忘了登记 → 脚本报 FILE_NOT_REGISTERED → 补登记后再跑 → PASS
  • 删除文件忘了移除 → 脚本报 FILE_NOT_FOUND → 移除后再跑 → PASS
  • 改了章节号没改引用 → 脚本报 REF_SECTION_BROKEN → 修引用后再跑 → PASS
  • 正常情况下，每次改完规范文件跑一次脚本，3 秒出报告，不依赖人记

问题二：本地PRD与知识库的优先级冲突

痛点

项目的需求权威来源是知识库（项目概览/model-ops-knowledge/），本地PRD是测试设计用的缓存。同步规则是”以知识库为准”。但实际工作中反复出现以下场景：

场景 示例 旧规则的结果 应该的结果
用户质询后修正了知识库的错误 用户指出”供应商就是渠道”，知识库写的是”跨层级”，本地改为”同层级” 知识库同步时自动覆盖本地 → 用户确认的修正被冲掉 保护本地，知识库后续同步
测试视角筛除了知识库的验证点 知识库有”迁移脚本不含ALTER TABLE”等运维类验收，测试判定不该测，用例骨架中删了 知识库同步时恢复这些验收 → 测试视角整改白做了 保护本地筛除结果
知识库同步只改了一半 v3.0 知识库同步回退了 §8.1.4 的”跨层级”，但 §8.1.5/§8.1.7 的”同层级”没改 → 同一文件两种口径并存 无检测机制 → 不一致持续存在 冲突标记待人工裁决

核心矛盾：知识库是权威来源没错，但”知识库永远最新”这个假设不成立——知识库也会滞后、也会过期、也会只同步一半。

解决方法

本地裁决标注 + 同步检查矩阵：

判定标准（三个条件缺一不可）

条件 说明 不满足时
用户确认 质询结论、直接修正、补充确认——Agent自行推断的不算 不构成裁决，正常按知识库同步
与知识库有差异 内容、范围、口径上和知识库现存版本不一致 无差异则无需保护
方向是本地领先 本地改了，知识库还没赶上；而非知识库改了、本地要追 方向是知识库→本地时，正常同步

同步检查矩阵

场景 本地 vs 知识库 有标注 处理方式
知识库领先 本地 < 知识库 无 ✅ 正常同步（知识库→本地）
知识库领先 本地 < 知识库 有 ⛔ 暂停同步，输出差异清单，标记冲突待人工裁决
本地领先 本地 ≥ 知识库 有 ✅ 以本地为准，知识库后续同步
双方都有变更 本地 ≥ 知识库 有 ⛔ 暂停同步，人工确认后决定方向
无差异 本地 = 知识库 — 无操作

实际案例：F1 互斥校验

Sprint5 F1（responses入站协议兼容转换）中，用户确认”供应商就是渠道”，互斥为同层级而非知识库的跨层级。v3.0 知识库同步只回退了 §8.1.4，§8.1.5/§8.1.7 未同步回退，导致同一文件两种口径并存。

修复后：

  • §8.1.4/§8.1.5/§8.1.7 全部统一为”同层级”
  • §8.1.7 末尾追加本地裁决标注
  • 版本更新记录追加 v3.2

以后知识库再同步 F1 互斥内容时，检查到本地有裁决标注 → 标记冲突 → 不自动覆盖 → 输出差异清单人工裁决。
